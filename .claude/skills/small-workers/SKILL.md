# Маленькие воркеры вместо статики

В Slimly нет «утилитных» `object` со статическими функциями и нет классов,
которые делают всё сразу. Любая работа — это объект за интерфейсом, который
приходит в конструктор параметром со значением по умолчанию. Тогда состав
сервиса виден в его сигнатуре, а подменить любую часть можно, не трогая
остальное.

Разбор при этом не самоцель. Воркер — это одна работа, а не один метод:
пара-тройка методов внутри одной работы читается лучше, чем та же работа,
размазанная по трём файлам.

## Правило

```kotlin
// ❌ так не делаем
object ImagePipeline {
    fun write(source: Uri, destination: Uri, settings: Settings) { … }
}

// ✅ так делаем
interface ImageEncoding {
    fun write(source: Uri, destination: Uri, settings: ImageEncodingSettings)
}

class ImageEncoder(
    private val reader: ImageSourceReading = ImageSourceReader(),
    private val metadata: ImageOutputPropertiesComposing = ImageOutputProperties(),
    private val writer: ImageDestinationWriting = ImageDestinationWriter(),
) : ImageEncoding { … }
```

Вызывающая сторона пишет `ImageEncoder()` и не знает про состав. Тест
подставляет свою реализацию любого шага.

## Как разбивать

1. Выпиши, что тип делает, глаголами. Каждый глагол — кандидат в воркер.
2. Соседние глаголы одной работы собери обратно в один воркер. Дробить
   дальше стоит, когда у части появляется свой смысл: другой вызывающий,
   своя замена в тесте, своя причина меняться.
3. Один воркер — один интерфейс — один файл. Имя интерфейса — действие
   (`ImageEncoding`, `VideoTranscoding`), имя реализации — исполнитель
   (`ImageEncoder`, `VideoTranscoder`).
4. Главный тип после разбора — сборка: он раздаёт работу и не содержит
   ни байта самой работы. Сборка оправдана, когда шагов много; ради двух
   вызовов подряд её не заводят.
5. Зависимости — `private val` типа интерфейса, приходят в конструктор
   значением по умолчанию. Никаких синглтонов и `Companion.instance`.

## Потоки

- Долгая работа уходит на `Dispatchers.IO`, а изоляцию состояния держит
  `Mutex`. Компилятор за это, в отличие от Swift 6, не отвечает —
  дисциплина на нас.
- Прогресс и события отдаются `Flow`: отмена подписки останавливает работу
  так же, как отмена `AsyncStream` на iOS.
- Всё, что трогает UI и роутер, живёт на главном потоке.

## Где остановиться

Разбор зашёл слишком далеко, если:

- воркер — обёртка в одну строку над чужим вызовом;
- сборка существует только чтобы вызвать два воркера подряд;
- у интерфейса не будет второй реализации и его не подменяют в тесте;
- имя воркера пришлось выдумывать.

Разбор не доделан, если:

- работа лежит в `object` со статическими функциями;
- тип длиннее ~150 строк;
- методы типа про разное: одни про файлы, другие про сеть, третьи про формат;
- из конструктора не видно, из чего тип собран.

## Когда статика допустима

- Мэпперы типа на себя: `ImageFormat.matching(extension)`, `VideoCodec.mime`.
- `private const val` — константа внутри воркера (порог, доля, лимит).

## Чек-лист перед завершением

- [ ] Нет `object` со статическими функциями, кроме мэпперов форматов.
- [ ] У каждого воркера есть интерфейс, вызывающая сторона держит его тип.
- [ ] Нет воркеров-однострочников и сборок из двух вызовов.
- [ ] Все зависимости видны в конструкторе и имеют значение по умолчанию.
- [ ] Тип не превышает ~150 строк.
- [ ] `./gradlew detekt ktlintCheck` молчит.
